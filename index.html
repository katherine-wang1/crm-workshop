Security primer

🔒 You decide what Claude can do

Every app you connect gives Claude a set of actions it can take. For each action, you choose one of three settings:

✅Always allowClaude does it without asking.
✋Needs approvalClaude asks you every time before doing it.
🚫BlockedClaude can never do it.

This is how you control what agents do on your behalf. A good rule of thumb: reading data is low risk, changing it is higher, and deleting or sending things is highest.

Not every setup works this way. Different AI apps (like Claude and ChatGPT) and different services you connect (like Gmail and Outlook) give you different levels of control. Some let you set each action separately, and others are all-or-nothing. Before you connect something, check what you're allowing.

For this workshop, we're using Always allow. The base is a practice CRM you just built, with nothing sensitive in it. You'll see every action Claude takes in the chat, and you can check the results in Airtable. Approving dozens of steps one by one would slow you down while you're learning. This is a personal choice, and you can change it anytime on this screen.

Personal or Stanford account? Some of you are on personal Claude accounts and others on Stanford accounts. Stanford accounts don't let you pick Always allow for a whole group at once. You can either click each tool individually to allow it, or approve tools on the fly as you walk through the workshop.

Why two files? So everyone can get the same instructions, and only one small file changes per person. If your base were written inside SKILL.md, we'd need a different SKILL.md for every student.

Now look at them in Claude. After the upload you're already on crm-company's page. The skill has two tabs:

  • Overview: the name and description. This is the part Claude reads to decide when to use the skill.
  • Contents: the files. Click SKILL.md, then crm-config.txt, to read each one.

Notice that SKILL.md on the Contents tab starts at the title. The name and description are on Overview.

There's no single right structure. A few ways it could have gone:

  • Config could live inside SKILL.md. Fine for a skill only you use. We split it out so one SKILL.md works for everyone.
  • You could add reference files, like a schema file or example outputs, for Claude to read when it needs them.
  • You could share one config across several skills.

The skill you build in Step 6 may end up structured differently. That's the point.

6Part C · Build your own

Build your own: crm-brief-me

The problem: you have a conversation coming up. You may have talked to this person before, but you can't remember what about, what you promised them, or what they're working on now. Think about what that's like for you: what do you usually scramble to find, and what would actually help in the five minutes before a chat?

You'll build this skill on your own using Claude's skill builder. You can have the skill do whatever would be most helpful in your day to day.

1Open the skill builder

In Claude: Customize (left sidebar) → Skills → + Add (top right) → Create with Claude.

Up for an extra challenge? Create a skill has you write it from scratch.

2Write your request

The skill builder is a chat. You describe what you want, it asks you a few questions, writes the skill, and can test it before you save. It can already use your Airtable connector, so you don't need to explain every field. You just tell it which base to use and how the tables connect. That's the bottom half of the prompt below.

Copy the prompt, paste it into the builder, and fill in the blanks at the top in your own words. A few words each is enough. Think about what you want out of it: there's no right answer.

3Answer the builder's questions, test on Maya, save

The builder will ask you a few things. Answer them in your own words.

Why test? A skill is a set of instructions Claude follows every time, so a gap in the instructions shows up every time too. Testing on someone already in your CRM lets you check the result against what you know is there: did it find your conversation with Maya, get her action items right, and say what's missing instead of guessing?

The builder won't always offer to test, so ask it: "Test this on Maya Chen before I save it." If something's off, tell the builder what to change and test again. Save once the brief matches Airtable.

Notice your skill has one file, not two. Why did we include a config file for the skills we gave you?

The skills we gave you go to every student with the same SKILL.md. Only the settings change, so this site could fill in a config file without touching the instructions. Your skill is built for one person, you, so the destination can live inside it, in its "My CRM" section. (The skill builder also saves a single SKILL.md.) Neither is wrong: structure follows who the skill is for.

Short on time, or the builder isn't cooperating? Upload ours and move on. You can build your own later.

Side quests

The four core skills keep your database up to date. Side quests go beyond that: each one extends the core build and teaches something the core build doesn't. Pick any, in any order. Each takes 15 to 20 minutes.

Four of the five put Claude on a timer with a scheduled task, so it works while you're away. Short on time? Start with Side quest 3: no scheduling, no new connectors.

A scheduled task is a prompt you save once, and Claude runs it on a timer: every weekday morning, every Monday. So far your skills only ran when you asked. A scheduled task runs them for you.

A run can use your skills and connectors, just like a chat. So a task's prompt can be one line, like /my-keep-in-touch, and the skill does the rest. That's one more reason skills are worth building: you write the logic once and reuse it anywhere, in a chat or on a schedule.

Facilitator only: Stanford accounts don't support cloud runs right now, so a scheduled task runs on the student's computer (awake, Claude desktop app open). Personal Pro/Max runs in the cloud. Plan requirements deliberately not mentioned to students.

Why these settings

  • Looks back 3 days: Monday's run covers the weekend. Runs overlap on purpose, and the prompt skips anything already in your CRM, so nothing is logged twice.

crm-person and crm-company save with no one watching. Why does the task send past meetings to you instead of running crm-capture-convo?

Adding a person or moving Last contact forward only adds information. If it's slightly off, nothing is lost and you fix it in Airtable. Capturing a conversation replaces Next action with what AI read into it, which is why capture shows a preview and waits for you (Step 5). On a timer, nobody reads that preview: the run either stalls or saves something unchecked. So the rule is: a skill can run unattended when its mistakes are cheap to spot and undo.
